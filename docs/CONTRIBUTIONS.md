# 复现、改进与证据边界

## 项目定位

这是面向零售服务 Agent 的研究型工程项目：把评测、诊断、优化和回归验证接成可追溯闭环。淘宝提供流程启发，开源框架提供可执行对象与优化器，论文提供实验逻辑。它不是淘宝内部生产系统或模型权重的完整复刻。

## 个人改进：可定位的分层失败反馈

将一次失败整理为：层级→业务规则→实际event ID→失败理由→归因类型→可修改的Agent提示位置及建议。与GEPA正常的文字反馈比较，只优化同一Agent提示词，不连同工具、用户模拟器、Rubric一起改。对data/rubric/unknown原因不提供Agent修补建议。

可检验例子：工具返回“submitted”却回复“资金到账”。反馈应指向CNT、提交/完成区别、该工具事件与最终回复、agent.md中的结果陈述约束。未经用户确认执行退货则属于TCC；如果工具回包丢失，只能CTX弃判，不能虚构一次Agent执行失败。

这属于**反馈协议与评测工程的组合改进假设**。GEPA已经具备文字反思和执行轨迹反馈；没有证据证明“结构化反馈”本身是全新概念，不声称首创失败归因、首次用GEPA或提出新优化算法。

新增相关工作进一步限定主张：Agentic CLEAR已有多粒度分析，AgentDebug已有根因定位与纠错反馈，AgentEval已有依赖传播建模，Who&When研究归因Agent与步骤。因此个人工作应表述为“零售任务上的证据约束反馈适配与固定预算验证”，而不是“首次提出分层评测/失败归因”。当前cause仅为候选归因，不等同于干预验证的根因。

## 哪些结果可以支持主张

- 相同预算、同一Agent模型/用户/评分协议下，A3相对A2在40个独立测试任务上有稳定收益，报告CI与三种子差异。
- 去层级/去证据定位的消融表现与假设一致，且覆盖率、长度、实际调用和错误数不存在明显不公平差异。
- 第二模型获得同方向收益；若不成立，明确限制为原模型/任务分布。
- 修复案例中，规则与证据定位有人工认可；不是只提高Judge自己的标签通过率。

## 哪些结果不足以支持主张

- 只在train改写任务或dev提高；只比较A0而没有正常GEPA；挑最好的优化种子；多次看测试后再改prompt。
- 因CTX大量弃判而得到高准确率；因修正清洗或Rubric使通过率上升，却称为Agent能力提升。
- 只展示固定fixture跑通、教师与学生一致率、单条成功轨迹或无调用成本的“提升”。
- API异常被记为0后让某组更差；不同Judge/模型/环境版本混用；把同任务多次采样算独立样本。

## 面试时可讲述的业务关联

核心问题是“版本发布前，如何知道Agent真的把订单操作做对、没有越权、没有误导用户，并能定位该改哪里”。展示一条从原始工具回包→Judge证据→人工复核→提示修订→未见任务回归的链路，再展示一个修复失效/副作用案例。用独立任务结果、失败误放行和调用开销支持结论。

可以如实写：搭建了基于DeepAgents与τ-bench的零售Agent评测工程，设计六层诊断和固定预算GEPA反馈对照，支持盲标与SFT导出。只有正式实验完成后，才填写实测提升、置信区间与成本；未验证的业务收入、线上规模和创新优越性不写入简历。
