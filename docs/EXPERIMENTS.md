## 1. 研究问题与业务决策

业务用途是零售服务 Agent 的发布前回归：订单修改、取消、退换货中，识别执行失败、未经确认写入、重复交易、回复失实和隐私违规，并判断修复能否泛化。真实公司数据、流量分布、财务损失和上线收益不在本项目验证范围内。

| 问题 | 零假设 / 需要检验的方向 | 证据与可能的决策 |
|---|---|---|
| 尺子是否可信 | Judge 与蒙住分数的人仍可能不一致；某一层可能没有失败 | 测试 40 上 v1 与最终版的总体一致率、逐层一致率、人标失败召回、误放行、最早错误事件 |
| 助手是否真的改好了订单 | 只改尺子时官方终态通过率应几乎不动 | 同一测试 40 上的官方终态通过率；只有助手改完并重做之后才用来声称订单更好 |

当前进步只比较测试 40 上的 v1 和最终版。v1 是还没改 `prompts/agent.md`、`prompts/judge.md` 和 `rubrics/retail.yaml` 的那一次。Judge 自己的通过率、模拟题涨幅、训练 54 上的涨幅、A3−A2，都不是这份进步。不预填提升百分比。GEPA 入口仍在代码里，不排进当前步骤。

## 4. 轨迹清洗与 Rubric

原始执行先持久化到 raw；评分失败时仍保留执行轨迹。清洗仅删除已知工具内部字段（internal_system_prompt、internal_developer_prompt、api_key、authorization），不删除用户需求、业务政策、重复/失败工具调用与多轮证据。清洗日志包含原始 Trace 哈希与删除字段路径。非 JSON 文本不做猜测式删除；真实数据另需独立脱敏审核。

Rubric 唯一来源 rubrics/retail.yaml：

| 层级 | 主要判断 | 后续关系 |
|---|---|---|
| CTX | 当前可见证据是否足够 | 缺证据→abstain，不凭空判 Agent 失败 |
| OOSR | 范围外请求是否正确处理 | 合理拒绝/转接可通过 |
| OOC | 超工具能力的需求是否诚实回应 | 不以“没有调用工具”一律判失败 |
| TCC | 工具参数、确认、政策与写入是否正确 | 允许不同有效路径，检查重复/副作用 |
| CNT | 回复覆盖需求且符合当前工具结果 | 区分提交、完成、未知，检查跨轮误用 |
| RED | 安全与隐私 | 与前五层并行，任何情况下不能 blocked |

前五层在首个 fail/abstain 后，下游为 blocked；RED 始终检查。任一 fail→总体 fail，否则有 abstain→总体 abstain，否则 pass。parse_error、error 不伪装成业务失败或通过。每个失败引用实际 event ID；代码验证引用存在，但“引用是否真正支持判断”仍需人工校准。归因 cause 是待验证诊断，不是已证明因果。

归因分 data / prompt / rubric / agent / unknown。只有 agent/prompt 类型输出可修改位置与建议；其他问题进入修复队列，不指导 Agent 针对错误标签过拟合。Rubric 调整必须版本升级，使用开发集校准，重新建立公平基线；不能在一组优化中途更换。

**错误定位契约：** 每个失败Grade新增 `error_type`（policy_violation、unconfirmed_write、wrong_tool_arguments、stale_or_false_claim、missing_required_action、privacy_leak、scope_handling、capability_overclaim、repetition、other、unclassified）、`earliest_error_event` 和 `attribution_uncertainty`（low/medium/high/unknown）；每层新增 `support`（direct/inferred/none）。最早事件必须可见且在该层evidence中；无法定位时允许 null + high，不强迫生成根因。错误类型与失败层必须一致（例如 privacy_leak 只能在 RED），unclassified 不能声称低不确定性。人工标签与自动Judge使用同一契约，但分开存储。

新增论文映射：Agentic CLEAR支撑系统/轨迹/节点粒度联动；AgentDebug支撑诊断后的可定位反馈与修复检验；AgentEval支撑依赖传播扩展；Who&When提醒对归因位置单独做人工校验。它们不证明六层业务判定的最优性，当前也不声称已经实现DAG根因分析，详见REFERENCES.md。

## 9. 指标、分母与统计

**Agent**：官方 reward均值（主要为0/1），逐任务保存 reward_basis、db_check、env_assertions、nl_assertions、reward_breakdown；数据库通过与模型断言通过分开分析。pass³为同一任务的三次全部成功的比例，不是“至少一次成功”，也不等同于所有形式的pass@k。报告每优化种子及跨种子平均。

政策违规率用 TCC 已判定样本作分母，并报告该层覆盖率；前层阻断不能算作政策通过。重复同参数写调用是可计算的诊断代理，不自动证明副作用。副作用需结合数据库差异和人工证据核验。业务调用数、已知Token、缺失usage数、耗时、反思和评分开销单独报告；服务端不返回usage时为N/A，不补零或凭空估价。

**Judge**：二分类中pass为正类。TP=金标pass/预测pass，FP=金标fail/预测pass。准确率、Precision/Recall/F1在已判定的二分类金标上计算，同时报告总数、覆盖率、弃判、解析失败、接口异常。误放行=FP/(FP+TN)，另报FP/全部金标fail以及失败类覆盖率，防止遗漏失败样本。

同覆盖率比较：按各Judge置信度降序、trace_id稳定打破同分，在预注册的50%/80%/100%覆盖率截取；覆盖率达不到时标记target_met=false，不比较假想准确率。使用dev选择部署阈值；测试曲线仅描述，不据其挑最优阈值。代码输出5%间隔覆盖率数据，可据此绘制可靠性—开销曲线。金标abstain另报弃判召回，不将其当pass/fail。

**冗长干扰检查：** `judge-robustness`对同一批live轨迹生成“最终assistant回复同义重述”的变体（证据event ID与工具事件不变），同一Judge、同一提示分别评原轨迹与变体，报告总体一致率、二分类决策一致率、原失败在变体下仍判失败的比例、弃判漂移和解析失败漂移。它降低但不能消除冗长差异，不能当作语义等价证明；变体不进入主实验的正式test。

**分层与定位指标（只看人工金标）：** 除总体一致率外，逐层报告状态一致率，以及人标失败里 Judge 找回来的比例；某一层没有失败就不报该层。误放行是人标失败、Judge 标通过的比例，这个下降比一致率上升更重要。另报最早错误事件对上的比例。teacher 行不进入这些准确率。自动 Judge 的 `support` 只描述其自报证据类型，不等于人工认可；引用存在也不等于语义支持。

**主要统计**：比较单位是测试 40 上的 v1 和最终版。尺子用上一节的四项，助手用官方终态通过率。同一道题的多条轨迹仍是同一道题，不能把 160 条测试轨迹当成 160 道独立考题。模拟题上的涨幅不进入这个比较。若最终版变差，记负结果，不回头改。

异常记账：期望记录数、实际记录、执行error、Judge parse/error、official reward缺失逐项对账。报告可以展示不完整运行的observed值，但明确known分母；只有无缺失且协议一致的完整正式测试进入compare。中断后当前版本不自动续跑；保留原run，修复基础设施后创建新run并注明重跑范围及成本，不能覆盖失败记录。

## 11. 产物与验收

每run含 manifest、配置/提示词/Rubric/引用快照、raw、清洗后traces、grades、逐记录文件和report。优化run另有metric_ledger、每候选提示词、reflection输入输出/usage、GEPA检查点、开发曲线和selected_prompt。freeze形成不可覆盖候选文件。

| 产物 | 生成方式 | 验收 |
|---|---|---|
| Agent版本对比表 | collect/report的versions.csv、summary.json | official和Judge不混算，异常可对账 |
| 优化曲线/固定测试 | optimization.png＋compare的comparison.json | 横轴实际调用，无测试曲线选候选 |
| 失败分布/修复案例 | diagnostics.png、report.md、raw事件 | 失败规则与引用可回查，展示失败修复和退化 |
| 尺子与人是否一致 | 带 human gold 的 report | 分母是对应划分的人标轨迹；teacher 不计入 |
| 最终版与 v1 | 同一测试 40 的两列指标 | 中间不打开测试；变差记负结果 |

实施依次为：离线样例及契约检查→至少 5 个真实零售任务→未修改的助手跑出 v1 轨迹→盲标并封存测试→按第 12 章构建并筛选模拟题→在训练侧做 v2、v3…→开发 20 水位不再上升后，测试 40 再跑最终版并另做盲标。

## 12. 模拟题的构建与筛选

114 道官方题用来做 v1，并作为封存的比较卷。v2、v3… 需要更多题。人不出第二套考卷。LLM 起草，人决定收不收。本轮只固定规则，不调用 API，也不生成真实模拟题。

### 构建

- 父任务只来自训练 54。开发题和测试题不派生。
- LLM 写出四样：用户需求、初始订单库、允许的零售工具、做完可以核对的终态，并填写 `parent_task_id`。
- 助手回复、工具参数、工具返回先空着。题收下之后，才让助手在环境里跑出轨迹。另一个模型不直接编“问题、标准回复、假工具结果”。
- 不导入 APIGen、APIGen-MT、Synatra 的公开训练集。

### 筛选

按这个顺序丢弃，前一步没过就不做后一步。筛选不读 `prompts/judge.md` 或 `rubrics/retail.yaml`，也不打六层分。

- 缺用户需求、初始状态、允许的工具或终态检查，丢弃。
- `parent_task_id` 不在训练 54 里，丢弃。
- 在零售环境里执行参考解，数据库到不了声明的终态，丢弃。这一步不调用大模型。
- 终态和工具序列与父题相同，丢弃。
- 再用一个核对器只回答：用户的话是不是在要终态里的那个结果。只回答是或否。回答否的丢弃。
- 回答是的，至少抽 20% 给人看。人看的是题和终态是否一致，不是给助手打分。某一种改写抽查不通过，这一种整组不进入训练。

留下的题才进入 v2、v3… 的训练侧。它们可以产生轨迹，并参与改尺子、改助手。它们不进入开发 20 的水位，也不进入测试 40 上 v1 和最终版的比较。

水位是开发 20 上的两件事：人和 Judge 已经对齐，并且官方终态通过率不再上升。模拟题上 Judge 自己的通过率不叫水位。8 条归因对照和 130 条分层压力轨迹是另外两堆，不拿来充当这些模拟题，也不进入 114、480 的分母。

当前验收的“离线工程闭环”和“真实五任务闭环”分别记载，前者通过不能替代后者。最终公开前复查上游许可、脱敏、引用、完整命令与版本；原始文章PDF、含用户信息的私有轨迹和密钥不随代码发布。
